# 第二章 总体设计

## 2.1 设计原则

1. 本地优先：配置、身份、密钥、会话、记忆、技能一律落在本机目录（默认 `~/.bolloon/`），软件不设中心账号，不做静默上报。
2. 无中心协作：节点间通过点对点网络自行发现与直连，中心只作为可选的中继与登记用途，缺失时软件降级而非不可用。
3. 状态可恢复：任何长耗时任务都以「目标—运行—检查点—恢复」的方式落盘，进程被强制终止后可从最近检查点继续，不会留下半成品。
4. 执行受约束：所有会产生副作用的工具调用都经过权限闸门与拒绝清单，工具参数先校验后执行，失败给出可读原因。
5. 事实单一来源：同一事实只保留一处权威副本（如模型配置只认 `bolloon-config.json`），配置损坏时进入待修复状态而不是静默回退默认值。
6. 如实报告：无法完成时如实说明失败原因，不编造结果、不返回伪造标识。

## 2.2 分层架构

软件自下而上分为五层：

1. 存储与运行态层：本机文件、浏览器本机数据库、内容寻址存储，以及初始化状态、定时任务、心跳等运行态。
2. 网络与身份层：节点发现、连接建立、地址穿透、中继转发，去中心化身份生成、签名与验证、消息投递。
3. 能力与协议层：大模型接入、提示词分层装配、上下文压缩、文档解析、工具库、技能、判断力协议、扩展协议。
4. 智能体内核层：推理与行动迭代循环、任务步骤编排、工具调用与校验、长任务监督与恢复。
5. 交互与服务层：本机服务端接口、命令行界面、浏览器界面、桌面外壳、移动端界面与移动端网关。

层间依赖自上而下单向：交互层调用内核层，内核层调用能力层与网络层，能力层与网络层通过存储层持久化。网络层不直接依赖交互层，因此可以在无界面模式下（守护模式、脚本模式）独立运行。

## 2.3 模块划分与依赖关系

软件主目录 `src/` 下按职责划分为十二档模块，依赖关系如下：

1. 程序入口与命令分发模块：位于最上层，负责解析启动参数并选择运行形态，不承载业务逻辑。
2. 启动引导与初始化模块：为内核准备上下文、记忆、人格、项目状态，并为启动提供就绪硬门禁。
3. 智能体核心引擎模块：被交互层调用，调用能力层工具与协议层模型，是业务中枢。
4. 生态扩展协议模块：以独立子目录方式提供目标、判断、模型上下文协议、子智能体、界面协议等扩展。
5. 大模型接入与上下文压缩模块：为内核提供统一的模型调用接口与上下文预算管理。
6. 约束层与安全模块：被工具调用路径与网络入站路径共同引用，属于横切模块。
7. 点对点网络与身份模块：被内核与交互层共同使用，对外提供消息、文档、任务委派三类能力。
8. 存储与运行态模块：被上述所有模块使用，提供持久化、定时与心跳基础设施。
9. 文档与知识处理模块：被工具库与知识整理流程调用。
10. 命令行界面与桌面外壳模块：仅依赖内核对外接口，不直接访问存储。
11. 自研运行时包模块：作为独立包发布，被内核按需引用，也可独立安装使用。
12. 服务端与界面模块：对外暴露接口，对内调用内核，是浏览器端与移动端的唯一入口。

## 2.4 关键设计之一：对话与工具执行主循环

1. 交互层提交用户消息后立即返回受理状态（HTTP 202），不阻塞界面。
2. 内核装配系统提示词分层（灵魂层、性格层、智能体文档层、项目上下文层、技能层、记忆层），按优先级与适用范围拼装。
3. 内核进入推理与行动迭代循环：模型给出下一步动作（含工具名与参数），内核校验参数、经闸门判定是否允许执行、执行工具并把结果回填到上下文，进入下一轮迭代，直到模型给出最终答复或达到步数上限。
4. 全过程通过服务端事件流推送：文本增量、工具调用状态、步骤事件、最终答复，界面据此实时渲染执行轨迹。
5. 迭代过程中的上下文超限按压缩策略处理：先折叠已完成片段，再压缩历史，最后按预算截断，压缩前后均保留可追溯的边界标记。
6. 并发工具调用与多轮工具结果在同一条事件流内保持顺序一致，保证界面显示的轨迹与真实执行顺序相符。

## 2.5 关键设计之二：长期任务的四段状态机

软件把长耗时任务建模为四段：目标、运行、检查点、恢复。

1. 目标：用户提出目标，软件记录判据（可以是用户给定并确认的，也可以是软件提出的候选判据，候选判据未确认则永不判定完成）。
2. 运行：由监督器按目标生成一次运行，运行前校验所需技能的快照（缺技能、技能被禁用、技能损坏或版本漂移都不启动运行），并把判据冻结在运行上。
3. 检查点：运行过程中把进度、证据、未决事项写入检查点文件，任何一步失败都保留已得证据。
4. 恢复：进程重启后，监督器扫描未完成的目标与运行，从最近检查点继续；不可自动恢复的情况转人工处理，不无限等待。

任务完成后需同时满足：判据存在且已确认、判据全部满足、存在对应证据、无未决事项、最近一次运行健康。任一条不满足则不判定完成。

## 2.6 关键设计之三：点对点通信与外部唤醒

1. 节点标识：每个节点生成去中心化身份（密钥对），用身份标识与公钥作为网络地址的一部分，节点间通信使用签名消息，收方先验签再处理。
2. 连接建立：优先局域网直连，跨网段时通过中继节点转发，连接参数（中继地址、保留时长）由服务端下发并在启动后复验协议可用性。
3. 消息类型：会话消息、文档传输、任务委派、目标唤醒事件、好友与群组控制消息。
4. 外部唤醒：等待外部结果的目标会登记等待条件（来源、关联标识、事件类型、过期时间），入站事件必须依次通过来源校验、关联校验、归属校验、过期校验、重复校验，全部通过才写入事实并唤醒目标；事件处理器本身不启动智能体，由监督器在下一轮统一继续。
5. 超时处理：等待超时自动转人工处理，不允许无限等待。

## 2.7 关键设计之四：存储与多端同步

1. 服务端与桌面端：本机目录下的配置文件、会话文件、事件记录文件；写入采用「先写临时文件再原子替换」的方式，避免中断写盘产生半份文件。
2. 浏览器端与移动端：使用本机数据库保存会话与消息，界面通过快照与增量两种方式与服务端同步。
3. 分布式：技能包、文档等内容以内容寻址方式保存，得到唯一标识后可分享；分布式存储不可用时降级为本地模式并如实提示。
4. 跨设备：以身份标识为主键做多设备登记，设备之间可互相发现并同步会话与目录。

## 2.8 部署形态

1. 命令行模式：终端交互界面，适用于开发与运维场景。
2. 浏览器模式：本机启动服务后通过浏览器访问，界面与服务同机。
3. 桌面模式：以桌面外壳封装，启动时自动选择可用端口并把端口号回报给主进程。
4. 移动端：原生外壳加本地页面容器，具备独立的本地智能体执行、扫码入网、无障碍自动操作能力。
5. 守护模式：无界面常驻，用于定时任务、心跳与长期任务监督。

## 2.9 主要技术选型与理由

1. 采用 TypeScript 作为主要开发语言：类型检查可在编译期发现接口不一致，适合多模块协作的大型工程。
2. 浏览器界面采用原生页面技术而不引入前端框架：降低打包体积与升级风险，移动端容器内启动更快。
3. 点对点网络采用成熟的分布式哈希表与中继协议实现：避免自研网络协议带来的兼容与安全问题。
4. 存储采用本机文件加内容寻址存储的组合：文件便于用户直接查看与备份，内容寻址便于分享与去重。
5. 移动端采用原生外壳加页面容器：一次开发覆盖两端，同时保留调用系统能力（后台任务、无障碍服务、扫码）的通道。
